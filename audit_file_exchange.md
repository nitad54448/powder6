# Powder 6 / GSAS-II audit: file exchange

Reviewed 28 October 2026, repository version 2.49.0. Review only; application code unchanged.

## Confirmed findings

### P1 — GSAS multi-bank imports silently lose every bank after the first

`js/parsers.js:749–750` finds one BANK header. The data loop breaks on the next BANK at line 766, and lines 819–822 return one pattern without a warning about additional banks. The application supports multiple patterns for other formats, so this is silent loss rather than a user-visible rejection of an unsupported format.

Reproduced through `detectAndParseFile('audit.xra', text)`:

```text
title
BANK 1 2 1 CONST 1000 100 0 0 ESD
100 2 400 30
BANK 2 2 1 CONST 2000 100 0 0 ESD
200 5 300 6
```

Result: `{tth:[10,11], intensity:[100,400], sig:[2,30], warnings:[]}`; no `patterns` or second bank. GSAS-II's importer discovers banks and supports repeated reads. Fix by returning one pattern per supported bank, or explicitly warn/reject a multi-bank file until implemented.

Reference: [GSAS-II GSAS importer](https://gsas-ii.readthedocs.io/en/latest/_modules/GSASII/imports/G2pwd_fxye.html#GSAS_ReaderClass).

### P2 — GSAS STD counter counts are discarded, changing statistical weights

`js/parsers.js:774–782` recognizes STD `I2,F6.0` fields but retains only their intensity; line 821 returns `sig:null` for every STD record. With counter count `n`, GSAS-II uses variance `I/n`. Powder 6 falls back to variance `I` for positive counts, so a record with `n=10` receives one tenth of the correct weight. Mixed counter counts change relative weights and the fit; uniform counts still alter chi-square and uncertainty scaling conventions.

Reproduced with two fixed-width records generated by `String(n).padStart(2,' ')+String(I).padStart(6,' ')`, with intensities 100 and 400. For n=1, 2 and 10, Powder 6 returns the identical intensities and `sig:null`. For n=10 the expected standard uncertainties are sqrt(10) and sqrt(40), rather than 10 and 20. Preserve the counter and derive sigma from `I/max(n,1)`, with explicit handling of nonpositive intensities.

Reference: [GSAS-II GetSTDdata source](https://gsas-ii.readthedocs.io/en/latest/_modules/GSASII/imports/G2pwd_fxye.html#GSAS_ReaderClass.Reader), particularly `ni`, `vi` and `w` in the nested reader.

### P2 — XYE export rounds valid positive intensities and uncertainties to zero

`js/rietveld/rv_gsas2.js:104` writes intensity with four fixed decimals and sigma with six; its `num()` helper also explicitly zeros small magnitudes. A dataset with `tth:[10,11]`, `y:[1e-7,1e-7]`, `sig:[1e-8,1e-8]` exports:

```text
10.00000 0 0
11.00000 0 0
```

GSAS-II's XYE importer assigns zero weight to these rounded zero intensities. Larger positive intensities with rounded zero sigma instead trigger GSAS-II's default counting weights, replacing the supplied uncertainties. This affects normalized or rescaled datasets. Use sufficient significant digits/scientific notation for all finite XYE values and preserve positive sigma.

Reference: [GSAS-II XYE reader](https://gsas-ii.readthedocs.io/en/latest/_modules/GSASII/imports/G2pwd_xye.html#xye_ReaderClass.Reader).

## Verified conventions and limits

- The generated `.instprm` header, colon-separated fields, PXC/PNC type, wavelength/doublet fields, and `Diff-type`/`Gonio.radius` are accepted conventions in [ReadInstprm](https://gsas-ii.readthedocs.io/en/latest/_modules/GSASII/GSASIIfiles.html#ReadInstprm). This was a source comparison, not an end-to-end import in an installed GSAS-II instance.
- `U,V,W` are Gaussian variances in centidegree squared, `X,Y,Z` Lorentzian widths in centidegrees. The simple profile conversion `U=GU+GP`, `W=GW+GP` follows sec²(theta)=1+tan²(theta). Its different mixing is disclosed.
- Zero and the README's Bragg-Brentano shift/transparency unit conversions are consistent with the compared formulas. Profiles with SL/HL deliberately lose their original asymmetry; the export warns that SH/L is a different model.
- Background instructions select GSAS-II `chebyschev-1`, which uses actual Chebyshev polynomials. GSAS-II's older `chebyschev` name uses powers instead. See [getBackground](https://gsas-ii.readthedocs.io/en/latest/_modules/GSASII/GSASIIpwd.html#getBackground).
- The ZIP is a transfer bundle, not a `.gpx` project. Scale normalization, preferred orientation, refinement flags/constraints, background and size/strain require manual setup; several differences are disclosed in its README. It should not be represented as a lossless project round trip.
- No GSAS-II `.instprm` or legacy `.prm` **reader** was found. Feeding the exported `.instprm` to the pattern loader yields “Could not parse any 2-column data”. Instrument export exists; instrument-file import is currently unsupported.
- GSAS data reading accepts constant-step CONST/CONS STD/ESD/FXYE only. TOF/TIME_MAP, logarithmic banks and FXY are unsupported. This is narrower than GSAS-II, rather than a physics defect in supported CW calculations.
- CIF tokenizer supports comments, quoted values, text fields and loops; multi-block structure imports are split by `readStructures`. B/U conversion is correct for isotropic atoms. Anisotropic tensors are neither imported nor exported as tensors; only the isotropic-equivalent fields are used. Pure anisotropic CIFs consequently acquire the fallback B=0.5 in `rv_commands.js:342`, without an anisotropic-data warning. This deserves an explicit import warning, even if tensor support remains outside scope.
- CIF `cif_structure.js` does not use the explicit symmetry-operation loop to determine the setting. It relies on HM/Hall/number resolution. Nonstandard operator-only settings require additional handling or a clear rejection. GSAS-II uses provided operators to check origin choice in its GUI; Hall/operator presence alone should not be treated as proof of setting preservation in every consumer.
